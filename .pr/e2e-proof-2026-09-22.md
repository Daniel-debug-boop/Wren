# Live E2E Proof Run — Wren Build Orchestrator v2 (2026-09-22)

## What was proven (for the first time in the project's history)

The multi-agent LLM build pipeline (`wren/app_builder/build_orchestrator.py`) was run
end-to-end against a **real LLM API** (OpenRouter, `openai/gpt-4o-mini`), with no mocks.

## Command

```bash
python -m wren.app_builder.build_orchestrator \
  --prompt "Build a Python CLI task manager called tasky: add/list/done commands, \
stores tasks in a local JSON file, includes unit tests and a README" \
  --api-key $OPENROUTER_API_KEY \
  --model openai/gpt-4o-mini \
  --base-url https://openrouter.ai/api/v1 \
  --output /tmp/wren-e2e-v2
```

## The generated app actually runs (verified live)

```
$ python src/cli.py add --title "Buy milk"     → Task added: Buy milk
$ python src/cli.py add --title "Ship Wren"    → Task added: Ship Wren
$ python src/cli.py list                       → 1. Buy milk [✗]  2. Ship Wren [✗]
$ python src/cli.py done --id 1                → Task marked as done: ID 1
$ python src/cli.py list                       → 1. Buy milk [✓]  2. Ship Wren [✗]
```

Persistence verified: `tasks.json` contains correct structured data
(`id`, `title`, `done: true/false`) across process restarts.

## Honest gaps found by this run (these are the next fixes)

1. **Generated unit tests fail out of the box.**
   `tests/test_task_manager.py` calls `mark_task_as_done()` while
   `src/task_manager.py` implements `mark_task_done()`, and one test hits
   `TypeError: object of type 'NoneType' has no len()`.
   → Root cause: each file is generated by an independent LLM call with no
   cross-file consistency pass, and the Validation pipeline never *executes*
   the generated tests.
2. **Validation is static only.** It parses/lints; it does not run the
   generated test suite. A "run tests" stage after generation would have
   caught gap 1 automatically.
3. **Minor UX bug in generated app:** `list` prints tasks but then also prints
   "No tasks available." (empty-check bug in generated `cli.py`).
4. **Import ergonomics:** `src/cli.py` uses `from src.task_manager import ...`,
   which requires `PYTHONPATH=.` instead of working from the project root as
   `python -m src.cli` or via an installed entry point.
5. **`oh build-*` CLI commands are template-based**, not LLM-based (keyword
   detection + static generators, 0.0s). The LLM pipeline is only reachable via
   `python -m wren.app_builder.build_orchestrator`. The advertised CLI surface
   does not match the actual capability.

## Environment note

- Python deps were installed with `poetry install --with dev` (dev group holds
  pytest). The fresh sandbox venv initially resolved to Python 3.10; fixed with
  `poetry env use /usr/bin/python3.12`.

## Verdict

**The core product loop is real and proven:** prompt → multi-agent LLM build →
files on disk → running program with persistent state. Remaining work to make
this reliable: self-healing test generation (run generated tests + feed
failures back to the LLM for correction — the `max_corrections` mechanism
exists but is not wired to test execution), cross-file consistency validation,
and routing `oh build-*` through the v2 orchestrator.
